## По итогам клиентского тестирования — открытые пункты

### P-17 — баннер крупнее вьюпорта

**Источник:** стенд B05b, клиентское тестирование 21.06.2026. Зафиксировано в `BUG_FIXING_V1.md`.

**Суть:** критерий видимости S1 (`intersectionRatio >= 0.5`, доля площади самого баннера) корректен по стандарту MRC для обычных размеров. Если баннер крупнее экрана устройства, 50% его площади физически не может оказаться в видимой области — измерение не стартует до уменьшения масштаба.

**Согласованное решение (21.06.2026):** логику измерения видимости не менять. Добавить отдельный предупреждающий флаг `banner_larger_than_viewport` — для desktop и mobile — как индикатор проблемы размещения для рекламодателя, не как модификатор Score.

**Объём:** детекция в теге → новое поле в схеме → флаг в `impressions` → миграция БД → отображение в панели. Сопоставимо с отдельной задачей.

**Текущий статус:** не начато. Ожидает приоритизации.

### P-03 — mobile не получает уровни S5 за удержание (аналог hover)

**Источник:** обнаружено при анализе кода в ходе тестирования 21.06.2026. Зафиксировано в `BUG_FIXING_V1.md`.

**Суть:** `touch_start_end_delta_ms` корректно собирается тегом (`s5.ts`), привязан к баннеру, но не используется в иерархии нормализации S5 (`scoring/normalize.ts`). Mobile-пользователь получает баллы только за `clicked`/`zoom`/`swipe`/`tap`, без уровня "длительное удержание без клика" — аналога desktop-hover.

**Что нужно:** ввести шкалу баллов для длительности касания (по аналогии с desktop `hover_500ms`/`hover`), согласовать конкретные пороги с клиентом.

**Текущий статус:** запланировано на вторую итерацию калибровки. Не начато.

### P-19 — `competing_ads_visible = 0` на стенде "теснота" — ожидает перепрогона

**Источник:** стенд B04, клиентское тестирование 21.06.2026. Зафиксировано в `BUG_FIXING_V1.md`.

**Суть:** не баг. `countCompetingAds()` матчит реальные AdTech-маркеры (домены, CSS-классы). Тестовый стенд B04 использовал визуальные плейсхолдеры без AdTech-разметки — счётчик закономерно вернул 0. Клиент планирует доработать стенд.

**Текущий статус:** ожидает повторного прогона с реалистичной AdTech-разметкой. Правка кода не требуется.

## Согласованные отступления от ТЗ

### Короткие полностью пассивные показы (<60 сек, 0 событий)

**Источник:** выявлено в ходе реализации P-15, `BUG_FIXING_V2.md` (23.06.2026).

**Суть:** показ длительностью менее `PRESENCE_IDLE_TIMEOUT_MS` (60 сек) при полном отсутствии пользовательских событий не обнуляется текущей формулой F_Presence (`time_since_last_event_ms > 60000`). Если показ завершился до истечения порога — условие никогда не выполняется.

**Решение клиента (23.06.2026):** оставить без изменений. ТЗ не определяет это поведение явно. Зафиксировано как согласованное отступление, не недосмотр.

### Сегментация по простою отключается после первого ухода вкладки в фон

**Источник:** `BUG_FIXING_V2.md` (23.06.2026), раздел "Граница объёма".

**Суть:** если вкладка хотя бы раз была свёрнута (`visibilitychange → hidden`), presence-обработчики снимаются вместе с финальной отправкой. Дальнейшая сегментация по простою для этой страницы не работает — только финальная отправка при закрытии.

**Решение:** осознанное ограничение, согласовано. Не дефект.

## Тег — незакрытые cleanup-пути

**Источник:** `README.md`, раздел "Технический долг — Мелкие улучшения тега".

### `IntersectionObserver.disconnect()` не вызывается при финализации

**Суть:** при финализации показа (`finalizeAndSend`) `IntersectionObserver` для S1 не отключается явно. Для статических страниц (одна загрузка — один показ) не проблема. Для SPA, где компонент баннера может размонтироваться и монтироваться повторно, наблюдатель продолжает работать до сборки мусора.

**Требуется:** `observer.disconnect()` при `session.sent = true`. Затрагивает `packages/tag/src/signals/s1.ts`.

### Интервалы S2, S7 и scroll-обработчик S3 не снимаются явно

**Суть:** `clearInterval` для S2 (`S2_SAMPLE_INTERVAL_MS`) и S7 (`S7_SAMPLE_INTERVAL_MS`), а также `removeEventListener('scroll')` для S3 не вызываются при финализации. Для одноразового показа на статической странице не проблема. Для SPA — утечка.

**Требуется:** хранить ссылки на `intervalId` и обработчики, снимать в `finalizeAndSend`. Затрагивает `s2.ts`, `s3.ts`, `s7.ts`.

## Backend и инфраструктура — мелкие улучшения

**Источник:** `README.md`, раздел "Технический долг".

### Drizzle Studio требует явной передачи `DATABASE_URL`

`pnpm db:studio` не подхватывает `.env` автоматически в dev-окружении — нужен ручной экспорт или префикс `DATABASE_URL=... pnpm db:studio`.

### Мониторинг успешности cron-бэкапов

Контейнер `backup` остаётся `alive` при сбое `pg_dump` внутри `crontab` — Docker `healthcheck` не видит ошибок задачи. Сбой бэкапа не приводит к видимому сигналу.

**Требуется:** либо проверка лог-файла в healthcheck, либо внешний алерт при отсутствии нового файла в `/opt/cpmind/backups/` за >25 часов.

### Cleanup job не подхватывает `processing`-батчи калибровки

**Источник:** разработка 30.06.2026.

**Суть:** `calibration_cleanup.ts` обрабатывает только батчи с `status='ready'`. Батчи, зависшие в `status='processing'` (если backend упал в процессе фоновой обработки), не истекают автоматически и не переходят в `failed`. Остаются в БД навсегда в промежуточном состоянии.

**Требуется:** добавить ветку в `cleanupExpiredDrafts()` для батчей с `status='processing'` и `created_at < now() - processing_timeout` (например, 10 минут).

## Frontend — известные поведенческие ограничения

**Источник:** разработка 30.06.2026.

### `onRowClick` не передаёт `userUuid` в URL детальной страницы

При клике на строку импрешена в `ImpressionsTable` навигация идёт на `/admin/impressions/:id` без `?userUuid=`. Кнопка "Назад" на детальной странице получает `searchParams.userUuid = undefined` и всегда возвращает в `/admin/impressions?userUuid=<ownUuid>` (собственный UUID администратора из токена), независимо от того, чей список просматривался.

**Требуется:** передавать `currentParams.userUuid` в `router.push` внутри `onRowClick`.

### Опции Campaign ID / Creative ID ограничены 200 значениями

Дропдауны Campaign ID и Creative ID в `Filters` строятся из отдельного запроса с `limit: 200` без активных фильтров. При >200 уникальных значений у пользователя список будет неполным без видимого предупреждения.

### Ручной выбор импрешенов сбрасывается при смене страницы

На `/admin/weights/recalculate` вручную отмеченные чекбоксы (`manualSelectedIds`) сбрасываются при переходе на следующую страницу пагинации. Состояние живёт только в рамках текущего набора видимых строк.

**Контекст:** намеренное ограничение v1. Обход — использовать "Выбрать все" с фильтрами вместо ручного выбора через несколько страниц.

### `ComboboxDatePicker` — формат даты расходится с `CalibrationFilterSchema`

`ComboboxDatePicker` возвращает строку формата `YYYY-MM-DD`. `CalibrationFilterSchema` ожидает полный ISO datetime с offset (`YYYY-MM-DDTHH:mm:ssZ`). Фильтрация по дате в воркспейсе калибровки не тестировалась — потенциальное расхождение форматов.

**Контекст:** для `GET /api/impressions` `dateFrom`/`dateTo` конвертируются на backend через `new Date(dateString)`, что принимает `YYYY-MM-DD` без offset и трактует как полночь UTC — фактически работает. Для `CalibrationFilterSchema` аналогичная совместимость не проверена.

### Accessibility кастомных компонентов

`Combobox`, `ComboboxDatePicker`, `SignalFilterModal`, `CreateUserForm`, `UserActionsMenu`, `TagConstantsPanel` (accordion, форма создания) — кастомные интерактивные компоненты без полной keyboard-навигации (`Tab`, стрелки, `Esc`), `aria-live` для динамических изменений, `focus-trap` внутри открытых поповеров.

## Архитектурные ограничения MVP

**Источник:** `README.md`, `ARCHITECTURE.md`.

### Нет полной мультитенантности

Ролевое разграничение (`admin`/`user`) реализовано. Изолированных инстансов или доменов на клиента — нет. Один сервер, одна база данных обслуживают всех пользователей.

### Один сервер без горизонтального масштабирования

Нет балансировщика нагрузки, нет реплик. При текущей нагрузке (тестирование + несколько клиентов) производительности достаточно (latency 2–19 мс p95 на `/api/collect`). При реальных рекламных объёмах потребуется пересмотр.

### Нет очереди сообщений

`POST /api/collect` обрабатывается синхронно. Калибровка — асинхронно, но без очереди (фоновая функция в процессе backend, чанками по 500). При росте объёма данных или количества одновременных батчей — Kafka или аналог.

### `tag_uuid` не защищён от подделки

`tag_uuid` виден в HTML-разметке страницы клиента. Отправка показов под чужим `tag_uuid` физически возможна и засоряет данные владельца, не давая доступа к чтению. Принятый риск MVP, нет планов закрытия в текущей итерации.

### Нет автоматических тестов

Ни одного unit/integration теста, кроме `@cpmind/shared` (формулы нормализации, vitest). Backend-функции (`buildWhereFromFilters`, `resolveSelectionWhere`, `approveCalibrationItems` и др.) не покрыты. Frontend — без e2e. Всё, что сейчас является "проверкой" — ручные curl-команды и браузерные тесты, выполненные разово, без CI, без регрессионного покрытия.
